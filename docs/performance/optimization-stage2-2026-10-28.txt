Optimization stage 2 -- static attachment interpretation and reference lookup
============================================================================

Changes
-------
AttachedEffects compiles each immutable ability's leading, led and starting-size
clauses once via a weak identity cache. It retains unsupported clauses as readable
effects without guessing numeric changes. Unit size, Character presence, legal
relationships and target-Afflicted state remain live decisions. Returned effects
own copies of mutable keyword lists. Changed ability objects get new compilation.

WeaponRuleReference indexes normalized ability names and ordered, distinct texts
by immutable ability-list identity. Missing shared indexes use an edition-specific
index weakly owned by the Dataset. This removes repeated scans/normalization of
the shared ability catalogue. Local definitions retain priority, including an
explicit local definition with empty text; edition boundaries, display names and
text order are unchanged. New dataset/list identities invalidate old results.
The original uncached lookup remains an internal comparison oracle.

This stage changes static interpretation and lookup, not the roster evaluator's
dependency/condition algorithm, database schema, catalogue revision storage or
UI framework. It does not introduce partial roster evaluation. The phone harness
also records PrepareAsync, RefreshPresentation and frame-wait durations separately
to guide the next UI work; those diagnostics exist only in PERFORMANCE_CHECKS.

Physical verification method
----------------------------
Use scripts/Publish-StandaloneAndroid.ps1 -PerformanceChecks, then
scripts/Measure-AndroidPerformance.py with the exact isolated APK, connected
serial, --iterations 10 --starts 5. It preserves production com.grimlist.mobile.
The default fixture has 3 and 20 entries, six operations and one unrecorded
warm-up per operation/size. Final timings include command, preparation, render
and two vsync callbacks. Reset/open and initial presentation are excluded.
Home is a refresh, not navigation from another page. Post-upgrade initialization
is distinct from first installation and ordinary cached process-cold startup.

scripts/Check-AndroidPerformanceApp.py runs native weaponMetadataChecks and
attachmentChecks against com.grimlist.perftest only. The first exercises build,
play, undo/redo, retained page and reopened profiles. The second exercises deferred
attachment choices, stale-result rejection, retry and page retention. Neither
tool clears production storage or sends any army outside the device/workspace.

The intermediate phone run preceded the final recovery-order correction and is
retained separately at artifacts/distribution-evidence/android-runtime-stage2-2026-10-28.
Its timings must not be presented as final-binary validation.

----------------------------------

Enhancement mean fell about 32%, attachment mean about 20%. These compare the
combined new build (including corrected metadata) with the previous build, not
an isolated causal A/B of either optimization. Home medians are effectively
unchanged (91 vs 90.5 ms). There is no universal speedup claim.

Four cached process-cold launches averaged 3,732 ms vs the previous 3,208 ms;
startup was slower in this run. Post-upgrade recovery took 24,881 ms. That is a

was 336,649 KiB (~329 MiB); after the workload 782,691 KiB (~764 MiB), vs ~794 MiB

Remaining roadmap
-----------------
Independent faction/shared-dependency revisioning remains the next architectural
phase. Then introduce reusable catalogue content and atomic manifests behind
Dataset, with history/reconstruction/interruption/corruption acceptance. Consider
dependency-based incremental evaluation last, preserving the full evaluator as
oracle and falling back to it for unknown dependencies. First-launch recovery
memory and attachment presentation remain measured targets; static-cache wins do
not prove that all UI or startup work is optimized.
