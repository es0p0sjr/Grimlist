GrimList Windows and physical Android measurements — 13 October 2026

Measurements and report only. No performance optimizations were applied to production source or deployed. All workloads used isolated disposable databases.

The main priorities are phone datasheet/rule preparation, Windows screen refresh work, and full-library startup. Direct database saves and army copying are small portions of the measured interaction delays.

Measurement method and limits:
  build: Release, current source snapshot with diagnostic instrumentation; Android trimming and AOT disabled as shipped
  startup: First install measured separately. Five fresh-process repeats with an existing empty database, then five with ten saved 20-entry armies. Windows opens Home; Android restores its roster on the saved-army runs. OS file caches are not reset.
  operations: Windows: 20 recorded samples per case. Android: 5 recorded samples per case in fresh-process batches after the long stress run aborted in Mono. One unrecorded warm-up per case. Each sample resets the fixture outside the timer. Ten saved armies. Commands use the shared session; native WPF/MAUI presentation follows. No touch-input injection.
  readiness: Two rendering callbacks after presentation. These are render-readiness proxies, not hardware display/input latency measurements.
  percentiles: Nearest-rank p95. Windows has 20 interaction samples per case; Android has 5, so its p95 equals the observed maximum and must not be treated as a reliable tail estimate. Startup has 5 samples per state.
  memory: Managed heap without forced GC; allocated bytes are cumulative allocation, not resident memory. Windows uses precise allocation sampling; Android interaction batches use approximate counters after runtime thread-suspension assertions in the long run. Windows working set and Android PSS are different OS metrics.
  - Synthetic Death Guard fixtures, not the user database.
  - Android receives its bundled Stratagem supplement; Windows uses its own normal bundled library. Library card counts differ, so ratios are not pure hardware comparisons.
  - Diagnostic timings include instrumentation overhead; its exact cost was not isolated.
  - Desktop command work runs through the shared async harness before native rendering; this does not measure production UI-thread blocking or input latency.
  - UI.RenderSubmit includes presentation calculations, control creation, and binding work; it is not a GPU-only or layout-only measurement.
  - The initial Windows datasheet case incorrectly called full Render; its 40 samples were excluded and replaced by 40 samples using the actual RefreshDetails path. Both raw runs are retained.
  - Background applications and OS caches were not reset.
  - No scrolling gesture/frame-jank benchmark: phone input injection is restricted.
  - No optimizations applied; there is no before/after speedup claim.

Validation: 236 original source/resource files hash-checked unchanged; 400 valid interaction samples. The initial 40 Windows datasheet samples were replaced with a corrected run using the production detail-refresh path.
The long Android run hit native Mono thread-suspension assertions and produced no valid final interaction samples. Android was remeasured in short checkpointed batches with approximate allocation counters. This is a diagnostic stability finding, not proof that the production app has the same failure or that allocation sampling caused it.
The precise allocation API has documented overhead; its use was removed from the revised phone interaction harness. Documentation: https://learn.microsoft.com/en-us/dotnet/api/system.gc.gettotalallocatedbytes?view=net-10.0
A stale incremental Android native-binding failure was caught during the diagnostic rebuild; a fresh intermediate/output build passed scripts/check_android_startup.py for ARM64 and x64 before the successful batched runs.
