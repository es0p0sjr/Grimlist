ANDROID PERFORMANCE IMPROVEMENTS - 2026-10-13

Implementation:
  Datasheet preparation no longer enumerates every possible attachment. Existing attached-unit links and detach controls remain immediately available.
  Choose a bodyguard unit / Choose a leader or support loads eligible actions on demand on a background task. Only that button waits; the rest of the page remains available.
  Completed and in-flight results are reused per entry while the army and library snapshots are unchanged. Edits, source reloads, undo/redo and opening another army invalidate the cache.
  Late results cannot populate a different page, entry or army state. Failed calculations offer a retry. Attaching still runs the complete current group and enhancement-slot validation.
  The expanded Home army-card tap target remains in this build.
  Test-only Android frame callbacks now retain/dispose their native wrapper after completion, with a timeout. Android diagnostic allocation counters use approximate sampling to avoid the previously observed Mono precise-sampling failure.

Method and limits:
  Physical Redmi Note 12 Pro+ 5G (22101316UG), Android 14; Release/Standalone build, .NET 10 Android, 2194 units / 6049 reference cards.
  15 fresh baseline samples and 40 optimized samples: five recorded per case plus one discarded warm-up. The same original AcceptanceWorkload fixture and operation sequence are used. Each operation runs in a fresh process; fixture resets and initial presentation are outside the timed interval.
  Datasheet/equipment select Plague Marines; enhancement and attachment use Lord of Contagion. The attachment case measures commit plus resulting presentation; chooser loading is measured separately.
  Readiness follows preparation, native MAUI presentation and two Choreographer callbacks. This is a readiness proxy, not touch-to-photon latency. No scrolling/jank benchmark was performed.
  Allocation counts include diagnostic overhead and are approximate. Nested timing scopes overlap; phase medians need not sum to the total median. Background activity and caches were not reset.
  Performance probes live only in an isolated diagnostic copy and com.grimlist.perfpass storage. No user army is used as a fixture. The normal package is updated in place.
  The full shared suite passed all 342 checks, including attachment combinations, recipients, effective datasheets, enhancement permissions and army summaries.
  Both diagnostic and production APKs passed the native MAUI startup-symbol check for arm64-v8a and x86_64. An incremental diagnostic package failed this check; the measured optimized build is the subsequent clean rebuild.
  Native chooser tests require a fresh isolated test installation: the first attempt collided with IDs from the separate operation fixture. This was test setup, not a user-roster failure.

Native chooser verification and production installation:
  All 37 native assertions passed: no eager candidate work; candidates match full session rules; actual MAUI controls offer the expected bodyguard; cached task reuse; pending results ignored after navigation, attachment, undo/redo, enhancement changes and library reload; invalidation; failed-task retry.
  Five recorded cold/warm pairs plus one discarded warm-up on the 20-entry fixture. First load median 3316.5 ms; cached load median 97.1 ms, both including native frame readiness.
  Two frame callbacks while loading: median 16.1 ms (range 15.3-171.5 ms). Session no-op while loading: median 1.61 ms. These show continued frame delivery and available session access; they do not measure physical scrolling latency.
