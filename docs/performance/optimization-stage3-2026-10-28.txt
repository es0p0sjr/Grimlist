Optimization continuation: enhancement presentation and reusable faction caches
Date: 2026-10-28

Implementation
--------------
Android enhancement choices now open on demand. The selected enhancement, its
description, removal action, budget and validation issues remain on the datasheet.
Shared EnhancementPresentation prepares each option with the existing authoritative
Enhancements.Select rules, retaining exact rejection messages. Work runs outside
the UI thread and ArmySession lock. Weak army/dataset identity caches share one
concurrent calculation per immutable input, with separate cheap summaries.
Exceptions are evicted so retries can calculate again. Actual selection still
passes through ArmySession validation. Pending results and button actions reject
stale snapshots; navigation cannot apply an old button to a previous unit.

FactionLibrary now has a factions-2 revision manifest and independently addressed
faction-content-1 payloads. Each faction's units/cards are hashed independently;
global ordering and exact profile/points/reference SourceInfo bindings belong to
the manifest. Source records are pooled, preserving null sources. Thus a provenance
timestamp or unrelated insertion need not duplicate unchanged faction content.
All other source-dependent semantics, IDs, aliases and unknown metadata remain in
the content and participate in its identity. A semantic recovery change is never
assumed equivalent simply because visible rule text is unchanged.

Shared ability definitions have their own reusable payload, loaded once when an
army needs a scoped view, rather than being deserialized with the Home manifest.
Dependency routes still cover all supported detachments and saved foreign units.
Views keep original ordering and exact source attribution; at most two are retained
by FactionLibrary. Full exports/imports continue to use the complete Dataset.

Payload hashes stream through SHA-256 without allocating one huge JSON buffer.
Existing files must pass their compressed checksum before reuse. A manifest is
published atomically after its payloads. Missing/corrupt derived files recover from
the authoritative repository. SQLite, historical snapshots and user data are not
migrated or modified by this cache-format change.

LocalPerformance adds opt-in timings for opening the database, loading/recovering
the library, constructing the manifest, reading faction/shared payloads and restoring
the saved army. Only the isolated performance app records them; production has no
listener or telemetry sink.

Scope and remaining architecture
--------------------------------
This is the first content-reuse part of the faction revision stage, not completion
of the full storage roadmap. Recovery still conservatively invalidates manifests
using Application/Core module identities. Cache misses still load/recover the full
library and recalculate dependency routes before reusing unchanged payload files.
Army-summary invalidation is still library-wide. No speedup is claimed for those
remaining operations merely because fewer files are duplicated.

Next: explicit independently maintained recovery/compilation contracts, dependency
and summary revisions, import-time projection preparation before activation, and
bounded manifest/payload retention with concurrent-reader handling. Then introduce
content-sharing in authoritative SQLite catalogue snapshots with migration/history/
interruption tests. Dependency-aware roster evaluation follows only with full-engine
comparison and conservative fallback for unknown dependencies. Smaller BLOB, statement
and serialization changes remain measurement-driven.
