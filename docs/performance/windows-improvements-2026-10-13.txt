GrimList Windows performance improvements - 13 October 2026

Implemented and measured: redundant metadata/editor refreshes removed, Home uses cached army summaries, attachment choices load asynchronously on demand and reuse unchanged immutable army/library snapshots. No Android UI or deployment changes.

Changes:
- Leaving unchanged name/limit fields no longer saves and rebuilds the editor. Leaving for Home, New Army or closing saves changed metadata without rendering the editor first.
- Home consumes ArmySession.LoadArmySummaries; search filters those summaries without recalculation. Existing invalidation covers source replacements, external saves, edits and removals.
- Opening an attachment picker computes its eligible choices on a worker thread. The session lock is not held during preparation, so other editing/navigation can proceed.
- Results are cached only for the same ArmyList and Dataset instances, per entry. Every edit/open/undo/redo/import invalidates those inputs. A completed request only populates the same live picker for the same entry and snapshot; failed requests can be retried.
- The shared snapshot overload delegates to exactly the existing complete proposed-group validation. Selecting an option still passes through session.Attach and its enhancement-slot validation.
- Attachment-summary links no longer refresh the selected datasheet twice.

Deferred attachment picker (separately measured, 20 cold + 20 cached samples):
  cold: property-setting handler 122.5 ms; next normal-priority dispatcher callback 123.3 ms; choices ready 832.1 ms; render readiness 979.6 ms (p95 1091.8).
  warm: property-setting handler 8.4 ms; next normal-priority dispatcher callback 8.9 ms; choices ready 10.9 ms; render readiness 11.6 ms (p95 155.2).
  The cold calculation was deferred, not eliminated. The UI can process work while it runs. Cached samples rebuild the picker on the same army/library snapshot, proving reuse beyond a single already-populated control. Changing the army or library requires fresh calculation.
  Dispatcher timing is a scheduling proxy; it is not a hardware-input latency or continuous frame-jank measurement. WPF opens the popup asynchronously, so property-setting time alone must not be mistaken for choices-ready time.

Method and limits:
  Before: .local/windows-profile-20261013 (same 20-unit Death Guard fixture, ten saved armies, 20 recorded repetitions per operation). After: this folder; one unrecorded warm-up per case. Isolated disposable databases only; production roster data was not used or changed.
  200 comparable post-change interaction samples + 20 layout samples + 40 picker samples. Eight ordinary operations use the shared async command harness followed by native WPF presentation; unchanged-fields and go-home run synchronously through the production handlers.
  Render readiness: UpdateLayout, two CompositionTarget.Rendering callbacks and Dispatcher ApplicationIdle. This is not input-to-photon latency. Background applications and OS caches were not reset. No test/build workloads ran concurrently with the measured batches.
  Layout probes were added only for the later frame/navigation/picker batches. They record UpdateLayout separately from rendering callbacks and the idle wait. Parent/child phases overlap and phase medians must not be added.
  Precise allocation counters and diagnostic timings add overhead. These are controlled synthetic workloads; other factions, roster sizes and loadouts may differ. Reported reductions apply to these measured cases.

Use the updated Windows app:
  Close the currently running GrimList window, then launch Start-GrimList.cmd. The existing launcher builds the updated Release source and preserves its .local data directory. A running process continues using its already loaded build.
