Startup and independent catalogue revisions
Date: 2026-10-28

Implemented boundaries
----------------------
CacheJsonContext supplies generated JSON metadata for faction manifests, payloads,
shared definitions, dependency tables and persisted army summaries. Timings separate
checksum verification, JSON metadata creation and deserialization. Unknown helper
payload types retain the normal serializer fallback; catalogue types use generated
metadata. This is a derived-cache change, not a new export or SQLite format.

The factions-4 startup manifest pools repeated SourceInfo records from detachment
definitions and reference coverage, in addition to existing unit/card bindings.
Loading restores every field and null source exactly. Header binding lengths and
indices are validated before use. A compatible factions-3 manifest with the same
repository revision, recovery/availability contracts and local evidence inventory
can migrate atomically without loading or recovering the complete library. Changed
contracts/source revisions and corrupt or incompatible caches take the full path.

LibraryRecoveryVersion now defines explicit normalization, static compilation,
availability and evaluation contracts. References, enhancement eligibility,
effective/weapon metadata and catalogue recovery have independent evidence stamps.
Directory.Build.targets hashes relevant embedded evidence at build time and emits
assembly metadata. Startup reads these small fingerprints, not every archive.
Application/Core module identities are no longer cache versions. Ordinary UI or
unrelated code changes do not force recovery when these contracts/evidence agree.

Downloaded recovery archives remain immutable commit-pinned sources. The local
bsdata-* directory/file inventory (names, sizes and UTC modification times) changes
the manifest key when archives arrive or are replaced. Inaccessible inventories
cannot certify a cache hit. Full recovery still applies its original source/hash/
edition/identity guards; this optimization never establishes new rule evidence.

Availability is cached by host faction/candidate faction pair. Each input fingerprint
includes the host/global lifecycle and override metadata, relevant detachment routes,
candidate name/faction/category/keywords/required detachments and source editions.
These are the facts consumed by UnitAvailability and AlliedRules. Unchanged pairs
reuse their result; changed inputs run the existing evaluator. Finding one eligible
unit is sufficient to include its faction, avoiding redundant checks of every unit
in an already accepted candidate faction. The current pair table replaces its
predecessor, keeping this new cache bounded.

Scoped summary revisions include faction content, applicable allies, saved foreign
units, metadata owners, global rules, relative unit/card ordering and runtime rule
contracts. An unrelated faction import no longer invalidates every saved army.
Unknown schemas/scopes fall back to the complete revision. Shared weapon explanation
text has a display revision; it does not invalidate unrelated numeric/validation
summaries. Relevant unit abilities and global rule cards remain calculation inputs.
Displayed provenance and shared definitions participate in view revisions.

Source names/editions are semantic inputs; dates, commit/archive IDs and URLs remain
exact display/recovery provenance. Recovery runs before semantic fingerprints are
computed. Full source records remain in manifests and exported datasets. A source
change that produces different recovered semantics changes the content revision.

Unchanged loaded faction payloads can be reused across an import/reload, retaining
immutable profile/ability identities and their existing compiled text caches. Each
new Dataset still receives the current header and exact source bindings. Payload
retention follows the existing two-view bound; summary dependency-key memoization
is bounded at 64 combinations. Old saved summary files are ignored in favor of the
single current summaries-2 file, whose individual rows validate their own inputs.

Contract maintenance
--------------------
- Normalization: bump when persisted library/reference compatibility interpretation
  changes. Update affected recovery contracts as well when their responsibilities change.
- Compilation: bump when static rule/fallback interpretation changes. Evaluation
  must also change when resulting pricing or validation behavior changes.
- Availability: bump for UnitAvailability/AlliedRules/lifecycle predicate or fact
  extraction changes; update the candidate/host inputs if a new dependency is read.
- Evaluation: bump when ArmyCalculator or its runtime dependencies can change saved
  totals/completeness/validation without a catalogue content change.
- Resource additions: ensure the consuming recovery stamp names the new evidence.
  Packaged resource bytes are checked against their build fingerprints in regression.
- New Dataset fields/schema or runtime uses of provenance require reviewing the
  semantic/header dependency projection before enabling fine-grained reuse.
- Layout changes require a new faction manifest/content contract or an explicitly
  validated migration. Missing/corrupt caches always remain disposable.

Limits and remaining roadmap
----------------------------
Actual source changes still load and recover the complete authoritative Dataset
before constructing the new manifest. Unchanged faction payloads/dependency results
and summaries are reused, but this does not make the importer incremental end to end.
Preparing projections before import activation, general cache-history retention,
authoritative SQLite content-sharing/migration and incremental roster evaluation
remain separate later phases. Full evaluation remains the correctness oracle.
