Interpretation
--------------
The broad earlier inference that the fixes made the app slower was stronger
than the historical comparisons justified. This controlled workload shows a
substantial benefit from static rule caching, small/variable typical differences
between current/full evaluation, and a detachment tail worth further profiling.
It neither proves nor disproves latency changes from storage/faction/UI phases,
or benefits from incremental evaluation on fully supported real-world rules.
Keep correctness fixes and conservative fallbacks. Do not roll back all work
on the basis of unmatched timing snapshots or chase percentage changes without
their absolute delays, variability and actual interaction context.

Question and scope
------------------
The user requested a controlled comparison after separate historical/current
timings suggested slower editing. Report absolute milliseconds and variability;
percentage changes alone do not establish a meaningful user-visible difference.

The exact earlier diagnostic Android binary was not retained. Therefore this is
NOT an old-versus-new release comparison, nor a test of every architecture change.
It isolates two current rule optimizations while preserving the same correctness
fixes, catalogue, roster, storage, frontend and runtime in a single binary.
It cannot attribute a whole-app change to catalogue storage, faction loading,
UI retention or a historical importer fix, because those are held constant.

Modes
-----
optimized: normal current behavior (incremental reuse and static rule caching).
full: cross-snapshot effective-rule reuse disabled; static rule caching retained.
uncached: full evaluation plus static prose-rule caching disabled.
Immutable same-snapshot evaluation caching remains enabled in every mode.
The full modes still use the current evaluator, including dependency observation;
they are controlled bypasses, not a reconstruction of the old source code.

Safety and implementation
-------------------------
Core bypass controls are compiled only with IncludePerformanceChecks=true.
The standard build has no ControlledPerformance type or mode branches. Mobile
exposes its comparison intent only in com.grimlist.perftest. Existing production
APK/MSI packages, the user's installed phone application and live libraries were
not replaced. Standard diagnostic publishing is used; one diagnostic APK remains.
The PC host uses a separate marked disposable library and refuses an existing
unmarked directory. No repository source copy was made.

AcceptanceWorkload gained optional diagnostic-only parameters: entry-count
filter, warm-up count and an outside-timing verification callback. Existing
callers retain their previous default behavior. Current frontend rendering is
used on Android; Windows measures shared commands, not WPF presentation.
Android intervals start at command dispatch and end after preparation/rendering
and two frame callbacks; they do not include opening a picker or human tap time.
The Home workload refreshes an already-presented Home screen, rather than timing
the complete navigation from another page. Do not average unlike actions into
a single claimed whole-app runtime.

Method
------
Real 20-entry Death Guard workload: add unit, equipment, enhancement, attachment,
detachment and Home. Three excluded warm-ups per action, then eight samples.
Twelve fresh-process blocks, four blocks per mode, produce 32 samples per action
and mode (576 measured actions per platform). A separate preparation run is
excluded. Windows and physical Android run on separate hardware after publishing
has finished; no compilation overlaps timed PC runs. ADB polling/report collection
is light host activity, not app execution on the PC.

A source search briefly overlapped Windows block 03 (uncached). Its samples
remain included, not silently dropped. Use the other balanced groups as a
sensitivity check; do not attribute that block's extra variability to app code.
Excluding its entire three-mode group leaves optimized-versus-uncached savings
in all other groups: mean reductions of 123 ms add, 102 equipment, 213 enhancement,
274 attachment and 115 detachment. This is a labelled post-hoc sensitivity check;
the primary results above retain every sample.

Balanced sequence, grouped in threes:
optimized/full/uncached; uncached/full/optimized;
full/uncached/optimized; optimized/uncached/full.
Each group contains every mode, and average order position is equal across modes.
Two-second inter-process pauses, warm derived/filesystem caches, no forced GC
between edits, no OS cache reset or CPU-frequency/power-profile changes. User
background applications/services remain active. Phone battery/thermal reports
are captured before and after each block. This is a controlled comparison on
the available devices, not a dedicated laboratory benchmark.

Every measured result is checked outside its timing interval against EvaluateFull.
Effective-state and ArmyResult hashes must match across all modes/iterations;
generated AddUnit entry IDs are normalized solely for comparison. Input hashes
and Core module identity must also match across every block on each platform.
The preparatory three-mode PC checks passed all six action-state comparisons.

Reported statistics: mean, median, nearest-rank p95, min/max, counts exceeding
500/1000 ms, command/presentation split, and allocation averages. Exploratory
95% t intervals use the four balanced group-mean differences (df=3), not all
individual samples as if they were independent runs. With only four groups,
intervals are descriptive evidence and not a universal performance guarantee.

The real fixture's optimized pilot fell back to full evaluation for every action
(no reused entries). This test can expose dependency-check overhead and static
parsing savings, but cannot demonstrate successful incremental reuse for rules
whose dependencies are fully known. Preserve conservative fallbacks; do not
weaken dependency checks to improve this benchmark. Earlier synthetic full-oracle
checks of supported dependencies remain separate correctness/performance evidence.

results; the labelled sensitivity result omits the entire group containing it
(blocks03-05), including both other modes, instead of dropping only slow samples.
