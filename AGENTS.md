- GrimList is an offline Warhammer 40,000 army builder and battle tracker for Windows and Android. There is no account service, application server, telemetry, or background battle synchronization.
- Both platforms use the same army/rules/import/persistence logic. Keep platform-specific code focused on UI, files, clipboard, sharing, PDF and SQLite adapters.
- Catalogue optimization (source only): SQLite schema 3 writes `GLCM1` manifests over immutable, hash-bucketed unit/reference pages with exact provenance bindings and 48-KiB binary chunks. Legacy JSON/GLDS1 history stays readable and is never rewritten at startup. New imports reuse unchanged pages; this does not reclaim existing historical full snapshots. Batch statements and army-entry indexes are shared through native adapters. See `docs/performance/catalogue-optimization-2026-10-28.txt` for measured tradeoffs and verification.
- Imports prepare/read-verify faction projections inside the committing transaction without changing the reviewed dataset. Points-only/custom imports preserve rules metadata; display-only recovery belongs to views. Snapshots still needing a separate authoritative recovery write retain normal recovery-on-open instead of certifying a cache that skips repair. Staged-cache leases span commit; preparation failure rolls back. Derived faction retention keeps two recent manifests plus leased readers, with one-day orphan grace. Never collect sources or authoritative history. Cache maintenance must not wait for SQLite while holding its filesystem lock; readers acquire leases before collection. Android uses non-exclusive/IMMEDIATE transactions for concurrent committed reads.
- Effective evaluation now compiles unit/card dependency facts, including inactive association conditions/repeats and roster predicates. Cross-entry reads and old/new attachment edges propagate dirty entries; add/remove/reorder/copy-label changes and muster nominations retain unrelated results. Army name/disposition changes reuse effective states. Other context changes, unknown dependencies/scopes/schema and nonconvergence retain full evaluation; newly encountered unsafe dependencies restart it. Both convergence phases and enhancement self-eligibility exclusion remain. `LibraryRecoveryVersion.Evaluation` is `army-evaluation-3`; weak caches must not retain an edit-history chain. Pricing/validation remain complete passes. See `docs/performance/import-evaluation-2026-10-28.txt`.

Save through ArmySession/ArmyStore rather than editing live SQLite directly.
Preserve army IDs, entry IDs, source provenance, imports, undo/redo and unknown-price states.
A numeric total alone is not proof of completeness or validity.

## Data sources and provenance

- **BSData 10e:** https://github.com/BSData/wh40k-10e (BattleScribe XML/CAT).
- **BSData 11e:** https://github.com/BSData/wh40k-11e (JSON). `BsDataClient` resolves main to a commit, downloads the pinned archive, and records commit/hash/date. `LibraryWorkflow` previews imports before apply; shared entries/dependencies are resolved by ID. Full repository ZIPs are preferable to isolated catalogues.
- **11e unit points:** https://github.com/BSData/wh40k-11e-mfm. `MfmMirrorClient`/`MfmMirrorParser` and the Core MFM overlay match faction/name/model sizes, preserve compatible saved MFM prices across BSData refreshes, and retain provenance independently from profiles. This mirror is not a guarantee of current official prices. Equipment, enhancements and detachment costs use their own source paths.
- **Official MFM:** `OfficialMfmClient` supports public official HTML/PDF and manual PDF/text input. Review warnings and observation dates; do not silently turn failed downloads or unknown matches into valid prices.
- **Reference rules:** BSData plus edition-specific Wahapedia pages (`https://wahapedia.ru/wh40k10ed/` and `https://wahapedia.ru/wh40k11ed/`). The generic reference pipeline acquires/caches, parses, matches, previews and audits provenance/coverage. `scripts/Acquire-ReferenceSources.ps1` and `docs/reference-acquisition.md` describe the workflow. Distinguish complete, partial, unknown and explicitly complete zero-card scopes. Do not invent rules, URLs or coverage to fill gaps.
- **Missions:** `data/missions/11e/*-missions-2026-27.json`, embedded by Application. Chapter Approved 2026–27 sources and metadata are in those files, `PrimaryMissionCards` and `DispositionPrimaries`. Disposition assignments cite GW Event Companion v1.2; mission cards cite the corresponding Wahapedia event-companion page.
- **Offline bootstrap:** `src/GrimList.Application/Resources/bootstrap/manifest.json` and `library.json.gz`. Recovery/reference resources in Application and core-stratagem resources in Core are also shipped. Preserve the manifests, hashes, schemas and source-aware recovery guards. Never package a developer/user database as the starting library.
- **Enhancement eligibility:** Bundle source Eligibility, IsUpgrade and selectable entry IDs directly. Recovery uses pinned source hash/edition and faction/detachment/entry identity; never gate it on full-card prose or price. Ambiguous/conflicting evidence stays unresolved. Both publish scripts run `scripts/Test-BundledEnhancements.ps1`; missing recoverable metadata fails candidate validation. See `docs/enhancement-eligibility.txt` for regeneration, legacy recovery and native test coverage.
- **Army-rule coverage:** `BsDataArmyRules` separates rule discovery from native roster roots and retains faction/source identities and conditional Applicability. Reference matching uses FactionContexts even without detachments. `ArmyRuleLibraryRecovery` restores matching pinned imports and retires explicit misattributions while preserving tombstones and overrides. The same bundled candidate gate now checks army-rule source/import/display coverage. See `docs/army-rule-recovery.txt`; bootstrap data release is `grimlist-11e-2026.10.16.2`.
- **Rules packs:** `data/rules-packs` and `docs/rules-packs.md`. Explicit overrides survive BSData refreshes. Partial packs must stay labelled partial.
- **Yellowscribe:** offline ROS export and explicitly requested uploads to https://yellowscribe.link/. Never send saved armies in automated tests; use local HTTP fixtures. The upstream parser is used for compatibility checks.
- **QR implementation:** `BattleQr.cs` is derived from Project Nayuki's MIT encoder. Keep `tools/qr_reference/LICENSE.txt`, the embedded license, the independent Python oracle and `tests/fixtures/qr/matrices.json`.

Use local cached fixtures for repeatable regression checks. Do not refresh rules/data as a side effect of packaging a UI release. For an actual rules/source update, verify the cited edition/version and preserve attribution; dates are provenance, not freshness claims. Ordinary HTTP/NuGet access has been restricted in this environment. Report unavailable acquisition; never claim a live download passed based on fixtures.

- `grimlist.db` contains saved armies and historical library snapshots. Preserve SQLite WAL/SHM/journal sidecars if present. Do not copy an active database as a supposedly consistent backup.
- Preserve `sources`, `reference-sources`, `battles`, and `battle-exchanges`. Derived caches are rebuildable; historical backups need inspection before deletion.
- Use disposable test libraries for synthetic imports, smoke checks and test battles. Never seed a user's live library with fixtures, uninstall the user's app or clear phone storage to test an update.
- Windows installer owns program files/shortcuts under `%LOCALAPPDATA%\Programs\GrimList`, not saved user data. Keep its upgrade identity stable. Android package is `com.grimlist.mobile`; preserve signing identity for in-place updates.
